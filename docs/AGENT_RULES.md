# Правила работы для ИИ-агента

- Один таск выполняется за один раз.
- Нельзя добавлять функции вне таска.
- Нельзя удалять существующую рабочую функциональность без явной команды.
- После каждого таска нужно давать отчёт.
- Если задача неясна, нужно выбрать самый простой безопасный вариант и записать это в отчёте.
- Перед завершением таска нужно проверить:
  - установку (`npm install`);
  - dev-сервер (`npm run dev`);
  - сборку (`npm run build`);
  - линтер (`npm run lint`).
- Нельзя подключать внешние сервисы, если это не указано в таске.
- Весь пользовательский интерфейс по умолчанию на русском языке.
- База данных, авторизация и файловое хранилище не добавляются, пока не будет отдельного таска.

## Правила работы с Git

- Один таск — один коммит после успешных проверок.
- Коммит делается только если `npm run build` и `npm run lint` проходят.
- Если таск выполнен частично или проверки падают, коммит не делается, а проблема описывается в отчёте.
- Формат сообщения коммита: `<type>: <краткое описание на русском>`, до 72 символов в первой строке.
- Допустимые типы: `feat`, `fix`, `refactor`, `chore`, `docs`, `style`, `test`.
- В теле коммита при необходимости приводится короткий список ключевых изменений.
- Запрещено коммитить: `.env`, cookie-файлы, файлы с реальными секретами, `node_modules`, `.next`, логи.
- Обязательно коммитить: исходники, конфиги, `drizzle`-миграции и `meta/_journal.json`, `package.json`, `package-lock.json`, `.env.example`, `docs/`.
- `git push` не выполняется без явной команды пользователя.
- Запрещены команды, переписывающие историю или уничтожающие изменения, без явной команды пользователя.
- В отчёте по каждому таску нужно указывать хеш и сообщение коммита.

## Правила на будущее (UI/UX и дизайн-система)

- При любых задачах, затрагивающих пользовательский интерфейс (страницы, компоненты, стили, тексты, формы, навигацию, состояния), обязательно применять релевантные проектные UI/UX-скиллы из `.agents/skills/`:
  - `ux-simple-first` — простота сценариев, тексты без техжаргона, обратная связь, подтверждение разрушающих действий, отсутствие тупиков;
  - `ui-audit` — визуальная иерархия, консистентность, полнота состояний, защита от перегрузки экрана;
  - `design-system` — токены из `src/app/globals.css`, семантические цвета статусов/форматов, единые варианты кнопок и бейджей;
  - `accessibility` — контраст WCAG AA, видимый фокус и клавиатура, `label`/`aria-describedby`, тач-цели ~44px, `prefers-reduced-motion`;
  - `forms-ux` — видимые `label`, подсказки, валидация до отправки, ошибки под полями, блокировка повторной отправки, явный режим `read-only`;
  - `responsive` — проверка на `375px`, `768px`, `1280px`, отсутствие горизонтального переполнения и обрезания.
- В отчёте по каждой UI-задаче обязательно указывать, какие скиллы были применены и какие конкретно пункты их чек-листов проверены.
- Запрещено менять бизнес-логику, контракты API, серверную валидацию, права доступа или схему БД под видом улучшения интерфейса.
- Новые цвета, радиусы, шрифты и размеры обязательно брать из проектных токенов (`src/app/globals.css`) и примитивов `src/components/ui/*` — не хардкодить hex/rgb/hsl, палитровые классы (`emerald-*`, `amber-*`, `blue-*` и т.п.) и произвольные размеры в обход токенов. Если нужен новый семантический токен (например, `--success`), он сначала добавляется в `src/app/globals.css`.
